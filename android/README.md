# 갤럭시 초기화 Android 앱

`V6.py`의 19단계를 Android 네이티브 앱으로 옮긴 프로젝트입니다. Windows EXE를 변환하는 것이 아니라 같은 DEX 헬퍼와 명령을 Shizuku shell(uid 2000)에서 실행합니다. 앱 ID는 `com.forholiday.galaxyreset`, 최소 Android 11입니다.

## APK 빌드

Android Studio에서 이 `android` 폴더를 열고 SDK 36과 Java 17을 사용합니다. SDK 경로는 Android Studio가 만드는 `local.properties` 또는 `ANDROID_HOME`으로 지정합니다.

```sh
cd android
./gradlew testDebugUnitTest lintDebug assembleDebug
```

설치용 APK: `app/build/outputs/apk/debug/app-debug.apk`. 서명된 테스트 APK이며 실제 기기에 설치할 수 있습니다. Android Studio의 Build > Generate Signed App Bundle / APK로 운영용 APK를 만들고 서명 키를 보관하세요. 같은 기기에 업데이트할 때는 기존 설치와 같은 서명 키가 필요합니다. CI의 임시 debug 키는 실행마다 달라질 수 있으므로 운영 업데이트에 사용하지 마세요.

루트 폴더의 DEX 6개·PNG 4개·네이버 지도 APK 세트·파일 관리자 APK는 빌드 시 자동으로 assets에 복사됩니다. Git으로 받은 경우 `git lfs pull`로 실제 APK 파일을 받아야 합니다. 네이버 지도의 기본 APK와 분할 APK를 포함해 초기화 앱 크기는 약 300MB 이상입니다.

GitHub Actions의 **Build Android APK**를 수동 실행해도 APK를 받을 수 있습니다. 새 워크플로 파일은 저장소에 push한 후 실행할 수 있습니다.

## 폰에서 사용

1. Android 11 이상 갤럭시 소유자 프로필(사용자 0)에 이 APK와 [Shizuku](https://shizuku.rikka.app/download/)를 설치합니다.
2. Wi-Fi 연결 → 개발자 옵션 → 무선 디버깅을 켭니다. 개발자 옵션이 없으면 휴대전화 정보 → 소프트웨어 정보 → 빌드번호를 여러 번 눌러 활성화합니다.
3. Shizuku에서 무선 디버깅 **페어링**을 진행합니다. Android가 표시하는 페어링 코드를 직접 입력합니다. 이어서 Shizuku **시작**을 누릅니다.
4. 초기화 앱의 **Shizuku 연결·권한 확인**을 누르고 권한을 허용합니다. 기존 권한이 있으면 앱이 자동으로 연결합니다.
5. 언어를 선택하고 **초기화 시작 → 모두 지우기**를 누릅니다.
6. 완료 또는 일부 실패 화면에서 결과를 확인합니다. 계정/e-SIM/접근 제한 파일은 수동 확인이 필요할 수 있습니다. 실패 단계만 재시도하거나 연결 중단 단계부터 계속 실행할 수 있습니다.
7. 배경화면·기본 홈 화면을 실제로 확인한 뒤 **전원 끄기**로 출고합니다. 재부팅하면 기존 Shizuku 프로세스는 종료됩니다. 13.6 이상은 Android 13 이상에서 설정 권한·이전 ADB 시작 이력·신뢰하는 Wi-Fi와 페어링 정보가 유지되면 자동 시작을 시도할 수 있습니다. 자동 시작이 되지 않으면 Shizuku에서 다시 시작하세요.

초기 무선 페어링·Wi-Fi 신뢰 승인·초기화 앱의 Shizuku 권한 허용은 기기에서 처리합니다. 아래 PC 준비 기능으로 설치·설정·USB 기동까지 처리할 수 있으며, 최초 승인 후 초기화 실행은 폰 단독으로 가능합니다.

## 기존 Windows EXE에서 폰 단독 사용 준비

`V6.py`의 18단계에서 네이버 지도·파일 관리자와 함께 **갤럭시 초기화 앱과 공식 Shizuku 13.6.0**을 설치합니다. 기존 초기화 앱과 Shizuku는 사용자 앱 삭제 대상에서 제외합니다. 같은 버전이나 최신 버전은 유지하고, 구버전은 `adb install -r`로 업데이트합니다. 서명 충돌이 발생하면 삭제 후 재설치하지 않고 실패로 표시합니다.

PC는 개발자 옵션·USB/무선 디버깅을 켜고, 필요한 설정·알림 권한을 부여하며, 두 앱을 배터리 제한에서 제외하고 Shizuku 서버를 USB로 시작합니다. 필수 앱 설치·설정·서버 시작을 확인하지 못하면 해당 기기의 작업을 실패로 표시합니다. 배터리 제한 제외 실패는 별도 안내로 남깁니다. 무선 디버깅을 켤 때 Wi-Fi 연결과 기기에서의 네트워크 허용이 필요할 수 있습니다.

처음 준비하는 기기는 **PC 작업이 끝난 뒤 전원을 끄기 전에** 다음 절차를 한 번 진행하세요.

1. 사용할 Wi-Fi에 연결하고 무선 디버깅에서 현재 네트워크를 허용합니다.
2. Shizuku → **무선 디버깅으로 시작 / 페어링**에서 Android의 페어링 코드를 입력합니다. PC가 USB로 Shizuku를 실행한 상태여도 이 무선 페어링은 별도로 필요합니다.
3. 갤럭시 초기화 앱에서 **연결하기**를 누르고 Shizuku 권한을 허용합니다. **권한 연결됨**을 확인합니다.
4. 이후에는 같은 신뢰 Wi-Fi에서 초기화 앱을 열어 사용합니다. Android 13 이상에서 Shizuku가 재부팅 후 자동 시작을 시도합니다. 자동 시작에 실패하면 Shizuku의 **시작**을 다시 누릅니다.

기존 페어링·권한은 PC 작업과 폰 초기화 작업에서 보존합니다. 매번 다시 페어링할 필요는 없지만, 페어링 삭제·앱 데이터 삭제·새 Wi-Fi 등의 상황에서는 재승인이 필요할 수 있습니다. USB 기동 성공만으로 무선 페어링 완료를 판정하지 않습니다.

초기화 없이 설치·설정만 준비하는 명령도 제공합니다. ADB가 PATH에 있어야 하며, `--serial`을 생략하면 연결된 기기를 준비합니다. 이 명령은 계정·앱·파일 삭제 단계를 실행하지 않습니다.

```sh
python V6.py --prepare-phone-only --serial DEVICE_SERIAL
```

Windows EXE에서도 같은 옵션을 사용할 수 있습니다.

```powershell
& '.\갤럭시 초기화 V8.exe' --prepare-phone-only --serial DEVICE_SERIAL
```

### APK 동봉 및 EXE 빌드

`phone-app/`에 고정된 서명의 초기화 APK와 공식 Shizuku APK, 버전·SHA-256 목록을 보관합니다. Android 앱을 변경하면 기존 기기와 같은 서명 키로 APK를 빌드한 뒤, 저장소 루트에서 다음을 실행해 동봉 파일을 갱신하세요. APK는 Git LFS 대상입니다.

```sh
python tools/prepare_phone_bundle.py
python tools/prepare_phone_bundle.py --check
python -m unittest -v test_phone_setup
```

첫 명령은 빌드된 초기화 APK를 복사하고 해시를 고정한 공식 Shizuku APK를 내려받습니다. 이미 받은 공식 파일은 `--shizuku-apk PATH`로 지정할 수 있습니다. EXE 시작 전에도 동봉 파일의 해시를 검사하므로, 누락·손상된 번들로 삭제 작업부터 시작하지 않습니다.

Windows에서 `pip install pyinstaller` 후 `pyinstaller V6.spec`로 빌드합니다. 결과는 `dist/갤럭시 초기화 V8.exe`입니다. **Build Windows EXE** 워크플로도 동봉 파일 검사와 준비 기능 테스트 후 빌드합니다. 이 과정은 Android APK를 다른 임시 키로 재빌드하지 않습니다. macOS에서는 Windows용 EXE를 빌드하지 않습니다.

## 실행과 복구

- 사용자가 확인해야만 실행되는 포그라운드 서비스입니다. 언어·글꼴 변경, 홈 화면 이동과 최근 앱 정리 중에도 작업은 서비스에서 진행됩니다. 화면과 진행 알림은 저장된 상태를 표시합니다.
- 앱 자신과 **Shizuku 관리자·삼성 인터넷도 삭제 제외**입니다. 18단계에서 필수 앱과 자신의 설치 상태를 확인합니다. 자신이 실행 중인 APK를 다시 설치할 필요는 없습니다.
- 자산은 앱 private cache → Binder 파일 디스크립터 → shell 소유 `/data/local/tmp/galaxy-reset`로 전달합니다. shell이 앱 private 경로를 직접 읽도록 가정하지 않습니다. DEX는 읽기 전용으로 복사합니다.
- 일반 실패는 다음 단계로 넘어가되 **실패/수동 확인**으로 남깁니다. 연결 단절·프로세스 종료는 현재 단계에서 멈추며 자동으로 삭제를 재개하지 않습니다. 재시도는 다시 삭제 확인 팝업을 거칩니다.
- 임시 비활성화 전에 패키지 목록을 내부 저장소에 기록합니다. `finally`에서 재활성화하며, 연결 단절로 복구가 불가능하면 목록을 유지합니다. 다음 실행은 재활성화부터 처리합니다. 복구가 완료되지 않으면 이후 삭제 작업을 진행하지 않습니다.
- 로그에는 계정 이름이나 e-SIM 식별자를 저장하지 않습니다. 원격 명령 출력을 제한하고 출력이 잘린 목록으로 앱을 삭제하지 않습니다.
- 알림 권한을 거부하면 알림창에 진행률이 보이지 않을 수 있습니다. 서비스 실행 여부는 Android 시스템의 실행 중인 앱 화면에서도 확인할 수 있습니다.

## 범위와 검증

이 도구는 공장 초기화/보안 삭제 도구가 아닙니다. 삼성 계정을 보존하고 V6가 대상으로 삼는 앱·사용자 파일·설정을 정리합니다. Android/One UI의 shell·SELinux 정책에 따라 보호 파일, 계정, e-SIM 삭제가 거부될 수 있습니다. 완료 표시가 기기의 모든 데이터가 완전히 없어졌다는 의미는 아닙니다.

원본 요구사항: `../docs/phone-app-requirements.md`. 문서의 디자인 링크는 읽지 못해 네이티브 UI로 화면 흐름을 구현했습니다.

단위 테스트는 앱/Shizuku 보존, 잘린 목록 거부, 위젯 영역 파싱, 비활성화 복구 기록, e-SIM 수동 처리 판정, 모델·언어·계정 규칙을 확인합니다. 실제 명령은 실행하지 않습니다. APK 빌드와 단위 테스트만으로 기기별 삭제 성공을 보장할 수 없으므로 아래 항목은 직원용 테스트 기기에서 확인하세요.

- 삼성/Google 계정 및 e-SIM 있는 기기의 결과, 실패 시 수동 안내
- Wi-Fi/Shizuku 중단 후 해당 단계 재시도 및 비활성화 패키지 복구
- 홈 키/런처 초기화/최근 앱 정리 중 서비스 유지와 화면 복귀
- 사진·휴지통·메시지·연락처·클립보드 잔여물
- 선택 언어와 보조 언어, 홈/잠금 배경 및 필수 앱
- S23/S24/S25/S26의 실제 Android/One UI 버전별 동작

API 구현 근거: [Shizuku 공식 API 안내](https://github.com/RikkaApps/Shizuku-API), [공식 UserService 샘플](https://github.com/RikkaApps/Shizuku-API/tree/master/demo).

## 1.0.1 실기기 수정

S26(Android 17)에서 확인한 문제를 수정했습니다. 계정 결과 파싱은 Android 정규식의 중괄호 해석 차이를 피하도록 문자열로 처리합니다. `dumpsys appwidget`은 전체 약 70KB 대신 Widgets 영역만 shell에서 추출해 Binder 출력 제한을 넘지 않게 합니다. 내부 저장소 검증은 빈 폴더와 시스템 `.nomedia` 및 썸네일 `.database_uuid`를 제외하고 실제 잔여 파일을 확인합니다. 실제 썸네일 이미지와 사용자 파일은 계속 잔여물로 표시합니다.

삼성 인터넷이 사용자 설치 앱인 경우에도 삭제하지 않습니다. 1.0.2부터 삼성 인터넷이 없는 기기는 설치를 건너뛰며, 실패나 수동 처리 항목으로 표시하지 않습니다. 설치되어 있으면 보존하고 활성화합니다.

## 1.1.1 화면 디자인

참고 Claude 아티팩트의 연결·시작·삭제 확인·진행·완료·일부 실패 화면을 네이티브 UI에 반영했습니다. 청록색 카드와 버튼, 언어 선택 카드, 배경 미리보기를 사용합니다. 상단 **화면 보기**에서 여섯 화면을 눌러 확인할 수 있습니다. 미리보기에서는 삭제 확인·재시도·전원 끄기 버튼도 실제 명령을 실행하지 않습니다. **실제 결과로 돌아가기**로 미리보기를 종료합니다.

진행 기록의 각 단계를 누르면 작업 내용·상태·마지막 결과를 확인합니다. 아이콘은 Google Material Symbols Rounded의 공식 SVG를 Android VectorDrawable로 변환한 리소스입니다. 라이선스와 출처는 `third-party/material-symbols`에 있습니다.

**연결하기**는 실행 중인 Shizuku에 권한을 요청·연결하거나, 꺼져 있으면 Shizuku 앱을 엽니다. Shizuku를 시작하고 돌아오면 자동 연결됩니다. 이 버튼이 OS의 페어링·Wi-Fi 신뢰 승인이나 Shizuku 시작 절차를 대신하는 것은 아닙니다.

## 1.1.2 전원 끄기 후 시작 화면

앱의 전원 끄기 명령을 보내기 전에 다음 실행 화면을 메인으로 저장합니다. 이후 앱을 다시 열면 이전 완료 화면 대신 메인·언어 선택 화면이 표시됩니다. 완료·실패 화면에서 **시작 화면으로**를 눌러도 이 선택이 유지됩니다. 마지막 실행 기록은 삭제하지 않으며 메인의 **지난 초기화 결과 보기**로 다시 확인할 수 있습니다. 새 초기화를 실행하면 이번 실행 결과를 다시 표시합니다.

S26(Android 17)에서 실제 재부팅 후 Shizuku를 수동으로 열지 않고 초기화 앱만 실행해 **권한 연결됨**과 **초기화 시작 버튼 활성화**를 확인했습니다. 이때 Shizuku 서버는 앱 실행 전부터 shell(uid 2000)로 시작돼 있었고, Wi-Fi가 연결된 상태였습니다. OS 잠금 화면은 사용자가 직접 해제했습니다. 이 검증에서는 초기화 작업을 재실행하지 않았습니다.

## 1.1.3 운영 화면 정리

상단 화면 보기·디자인 미리보기 메뉴를 제거했습니다. 단계별 작업 내용과 실제 결과를 확인하는 기능은 유지합니다. 완료 화면의 하단 버튼은 **시작 화면으로(왼쪽) / 전원 끄기(오른쪽)** 가로 배열입니다. 지난 기록은 메인의 **지난 초기화 결과 보기**로 열 수 있습니다.

## 1.1.4 진행 기록 스크롤

결과 상세와 진행 화면의 중첩 스크롤을 제거했습니다. 진행 기록의 행 위에서 위아래로 밀어 19단계 전체를 확인하고, 각 행을 눌러 상세 결과를 열 수 있습니다. 결과 화면으로 돌아가는 버튼은 하단에 고정합니다.

## 1.1.5 앱 종료와 기록 정리

상단 고정 제목을 제거하고, 앱 아이콘은 EXE의 `reset_icon.ico` 원본 로고로 통일했습니다. 뒤로가기를 2초 안에 두 번 누르면 앱 화면과 최근 앱 항목을 닫습니다. 실행 중인 초기화는 포그라운드 서비스에서 계속 진행됩니다.

1.1.8에서는 원본 로고의 색상과 모양을 유지하면서 흰색 배경과 사방 28dp 여백을 적용했습니다. 로고 자체가 런처 외곽에 잘리거나 꽉 차게 보이지 않도록 했습니다.

## 1.1.9 네이버 지도 교체와 직원 확인

네이버 지도를 5.12.4에서 **6.10.0.16 (61000004)**로 교체했습니다. 배포본의 실제 출처는 `nmap-bundle.json`에 기록합니다. APKPure 공개 미러에서 받은 기본·ARM64·xxhdpi APK 3개 모두 서명 검증을 통과했으며, 기존 네이버 지도와 발급자 인증서 SHA-256이 일치합니다. APK를 재서명하거나 분할 APK를 임의로 합치지 않습니다. 대상 S23~S26 갤럭시의 ARM64용 세트입니다.

PC와 폰은 설치 버전을 비교해 구버전만 업데이트하며, 더 최신 버전은 유지합니다. PC는 `adb install-multiple -r`, 폰은 설치 세션에 APK 전체를 기록한 뒤 한 번에 커밋합니다. 실패한 세션은 폐기하며, 서명 충돌 때 앱을 삭제하지 않습니다. 설치 후 버전·실행 화면 조회·프로세스 시작을 확인하고 강제 종료합니다. 이 검사는 첫 이용 약관·권한 동의와 지도/네트워크 로딩을 대신하지 않습니다.

새 배포본을 반영할 때는 전체 APK를 한 폴더에 모은 후 다음을 실행하세요. 서명과 패키지·버전이 일치해야만 가져옵니다. 이어서 Android를 같은 키로 다시 빌드하고 `tools/prepare_phone_bundle.py`로 EXE 동봉 앱도 갱신해야 합니다. 번들 검사는 Android에 들어간 지도 메타데이터와 PC 배포본의 일치 여부까지 확인합니다.

```sh
python tools/prepare_nmap_bundle.py --apk-directory APK_DIRECTORY --build-tools SDK_BUILD_TOOLS_DIRECTORY --source ACTUAL_SOURCE
```

초기화 시작 화면과 확인창에 **직원 전용 · 고객 실행 금지**와 데이터 삭제·복구 불가 경고를 표시합니다. **1.1.10부터 입력과 체크 절차 없이 취소 / 삭제 실행 버튼만 사용합니다.** 전체 실행·단계 재시도·중단 후 재개에도 같은 경고를 표시합니다. 취소·뒤로가기는 초기화를 실행하지 않습니다.

완료 화면의 전원 끄기를 확인하면 Shizuku 연결을 먼저 확인하고, 앱 내부 진행·결과 기록과 완료 알림을 지운 뒤 최근 앱 항목을 닫고 전원 끄기 명령을 보냅니다. 다음 실행은 기록 없는 메인 화면입니다. 취소하면 기록을 유지하며, 앱 재활성화 복구가 남아있으면 기록을 지우지 않고 복구 안내를 표시합니다. Shizuku 페어링·권한은 유지합니다. 이 기능은 Android 시스템이 관리하는 사용 통계 삭제를 뜻하지 않습니다.

## 1.1.13 앱 실행 시 Shizuku 자동 시작

**PC EXE로 최초 준비할 때는 코드 입력을 자동 처리합니다.** 잠금을 푼 기기를 USB로 연결하고 EXE를 실행하면 필수 앱 단계에서 시스템 페어링 창을 열고, 코드와 포트를 읽어 초기화 앱에 등록합니다. 초기화 앱의 Shizuku 권한 요청도 해당 앱 이름을 확인한 뒤 승인하고 연결 완료를 확인합니다. 잠금 해제·USB 디버깅 최초 승인은 직접 해야 합니다. 테스트한 Galaxy S23의 한국어·일본어 등 메뉴 문구를 기준으로 동작하며, 지원하지 않는 화면은 준비 실패로 안내합니다.

이 연결점은 `android.permission.DUMP`로 보호돼 일반 앱에서 호출할 수 없습니다. 인증 키를 PC에 복사하거나 Android의 승인 데이터베이스를 수정하지 않으며, 1회용 코드를 PC 로그에 남기지 않습니다. PC 자동화는 네트워크를 한 번만 허용하며 ‘항상 허용’을 임의로 선택하지 않습니다. 매장 네트워크를 계속 사용할 때는 해당 시스템 설정을 운영자가 직접 승인해야 합니다.

초기화 앱에 LibADB Android 3.1.1을 사용한 자체 무선 ADB 클라이언트를 추가했습니다. 메인·연결 화면의 **자동 시작 설정**에서 최초 1회 등록합니다. 기존 Shizuku용 페어링과 별도의 `GalaxyReset` 인증입니다.

1. **자동 시작 설정 → 페어링 시작**을 누릅니다. 코드 입력용 알림을 허용해야 합니다.
2. 개발자 옵션에서 **무선 디버깅**을 켜고 **페어링 코드로 기기 페어링**을 누릅니다.
3. 코드 창을 닫지 않고 알림을 내려 **초기화 앱 자동 시작 설정 → 페어링 코드 입력**에 6자리 코드를 입력합니다.
4. 설정 완료 후 앱으로 돌아옵니다. 이후 앱 실행 시 Wi-Fi·인증 상태를 확인하고 무선 ADB로 설치된 공식 Shizuku starter를 실행합니다. 초기화는 자동 실행하지 않습니다.

PC에서 부여한 `WRITE_SECURE_SETTINGS`가 유지되면 앱이 무선 디버깅을 켜는 작업도 시도합니다. Wi-Fi 연결, 시스템의 현재 네트워크 허용, 기기 잠금 해제와 최초 Shizuku 앱 권한 승인은 필요합니다. 시스템이 허용 창을 표시하면 직접 승인해야 하므로 모든 기기 상태에서 무조건 한 번에 연결된다는 보장은 없습니다. 인증이 취소되면 다시 페어링하도록 안내하며, 네트워크 오류만으로 인증을 지우지 않습니다. 인터넷 없이 로컬 Wi-Fi에서 동작하며 다른 기기의 ADB 서비스에는 연결하지 않습니다.

인증 키는 기기별로 생성해 Android Keystore AES-GCM으로 암호화한 뒤 앱의 백업 제외 내부 파일에 저장합니다. 앱 업데이트·진행 기록 삭제·앱의 전원 끄기는 인증 키를 지우지 않습니다. 앱 데이터 삭제·삭제 후 재설치·시스템 인증 취소 시에는 다시 등록해야 합니다. 기존 Shizuku에서 직접 시작하는 수동 경로도 유지합니다.

## 1.1.12 Shizuku 재연결

PC EXE의 폰 준비 과정은 `adb_allowed_connection_time=0`을 쓰고 다시 읽어 확인합니다. 개발자 옵션의 ADB 인증 자동 만료를 해제해 이미 허용한 인증을 계속 유지하는 설정이며, 기존에 인증한 PC에도 적용됩니다. 설정이 적용되지 않으면 준비 완료로 처리하지 않습니다. 삭제된 페어링 복구, Shizuku 자동 시작, 사용자에 의한 인증 취소 방지를 뜻하지 않습니다. 이미 페어링 목록에서 사라진 기기는 다시 핀번호로 페어링해야 합니다.

연결이 끊기면 상태에 따라 **Shizuku 시작하기 / 권한 허용하기 / 다시 연결** 버튼을 표시합니다. Shizuku가 실행 중이고 권한이 있으면 화면을 열어둔 동안 자동으로 shell 서비스에 다시 연결하며, 버튼으로 즉시 재시도할 수도 있습니다. 연결 중에는 중복 요청을 막고, 시간 초과 뒤에는 간격을 두고 재시도합니다. 연결 성공 시 초기화 시작 버튼을 활성화하며 초기화를 자동 실행하지 않습니다.

Shizuku 자체가 종료됐거나 기기를 재부팅한 경우에는 **Shizuku 시작하기 → Shizuku의 무선 디버깅 시작 → 초기화 앱으로 돌아오기** 순서로 진행합니다. 앱으로 돌아오면 연결을 자동 확인합니다. 기존 Shizuku 무선 디버깅 방식은 일반 앱에서 Shizuku 시작까지 대신하는 공개 API를 제공하지 않습니다. 페어링이 유지됐다면 보통 시작만 다시 하면 되며, Wi-Fi·무선 디버깅이 꺼져 있거나 페어링이 삭제됐다면 해당 설정도 필요합니다.

## 1.1.11 GitHub Releases 자체 업데이트

메인·연결 화면의 **업데이트 확인**을 누르면 공개 저장소 `w00ye0l/galaxy-reset`의 최신 정식 릴리스를 확인합니다. 초기화 앱 자체를 업데이트하는 기능입니다. PC EXE 업데이트나 네이버 지도의 독립적인 온라인 업데이트는 수행하지 않습니다. 새 초기화 APK에 동봉된 지도는 다음 초기화의 필수 앱 단계에서 버전을 비교해 적용합니다.

릴리스에는 아래 두 파일을 함께 올려야 합니다.

- `galaxy-reset.apk`: 기존 설치와 같은 서명 키로 빌드한 APK
- `galaxy-reset-update.json`: packageName·versionCode·versionName·APK 크기·SHA-256 정보

앱은 더 높은 versionCode만 제안합니다. 다운로드 주소를 해당 GitHub 저장소로 제한하고, 다운로드 후 크기·SHA-256·실제 APK 패키지/버전·설치된 앱과 동일한 서명 인증서를 검증합니다. 검증 실패·설치 취소·네트워크 오류 때 기존 앱은 유지됩니다. 다운로드·설치 중에는 초기화를 시작할 수 없습니다. 다운로드 중에는 앱을 열어두세요.

최초 1회 **이 출처 허용**을 켜면 Android 설치 확인창에서 업데이트를 승인할 수 있습니다. Shizuku가 꺼져 있어도 자체 업데이트를 사용할 수 있으며, 설치는 Android PackageInstaller가 처리합니다. 설치 후 앱을 다시 열면 됩니다. 기존 초기화 기록과 Shizuku 권한을 삭제하는 재설치는 하지 않습니다. 기기 보안 설정이 설치를 차단하면 해당 시스템 안내를 확인하세요.

### 앱 업데이트 게시

1. Android의 `versionCode`와 `versionName`을 올리고, 기존 서명 키로 빌드합니다.
2. `python tools/prepare_phone_bundle.py`로 PC 동봉 APK와 업데이트 JSON을 함께 갱신해 커밋·푸시합니다.
3. GitHub Actions의 **Publish App Update**를 최신 커밋의 브랜치에서 실행합니다. tag를 비우면 APK 버전에 맞춰 `app-v1.1.11` 같은 태그를 사용합니다. 같은 태그가 다른 커밋을 가리키거나 이미 릴리스가 있으면 실패하므로 버전마다 새 태그를 사용하세요.
4. 기본 동작은 **이미 서명된 `phone-app/galaxy-reset.apk`와 업데이트 JSON만** 초안 릴리스에 올리는 것입니다. 두 파일 업로드 후 정식·최신 릴리스로 공개하며, CI에서 임시 debug 키로 APK를 재빌드하지 않습니다. Windows 프로그램도 갱신해야 하면 수동 실행 시 `build_windows`를 켜세요. 이때만 EXE 빌드·준비 테스트 후 EXE ZIP과 SHA-256도 함께 게시합니다.
5. 기기에서 **업데이트 확인 → 다운로드·설치 → Android 업데이트 승인**으로 설치합니다.

버전과 일치하는 `app-v*` 태그를 푸시하면 APK만 게시합니다. **Build Windows EXE**만 따로 실행하면 기존처럼 Actions 아티팩트를 내려받을 수도 있습니다. 최신 정식 릴리스는 앱 업데이트용 두 파일을 포함해야 합니다. 기존 EXE의 초기화 로직·동봉 APK는 앱 릴리스만으로 바뀌지 않습니다.

## 1.1.16 네이버 계정 제거

계정 삭제 단계에서 기존 DEX 처리 후에도 `com.nhn.android.naveraccount`가 남으면, Shizuku shell로 삼성 설정의 계정 관리 화면을 열고 NAVER 항목 → 계정 삭제 → 삭제 확인을 진행합니다. 네이버 서비스의 탈퇴가 아니라 해당 기기에 저장된 계정·인증 정보 제거입니다. 계정 수를 무시하거나 로그아웃만 확인해 통과시키지 않고, 실제 현재 계정 목록에 네이버 계정이 없어야 완료됩니다. 삼성 계정은 선택하지 않습니다. UI 덤프는 임시 파일로만 읽고 즉시 제거하며 계정 이름·토큰을 로그에 남기지 않습니다.

잠금 화면, 다른 제공자, 알 수 없는 확인창, UI 조회 실패, 제거 거부, 남은 다른 비삼성 계정은 계속 실패/수동 확인으로 표시합니다. 화면을 켜고 잠금을 푼 상태에서 실행해야 합니다. 이 수정은 Android 앱에 적용하며 기존 배포 EXE의 로직은 그대로입니다.

### Windows 1.1.17 네이버 계정·지도 로그인 초기화

`V6.py`도 기본 계정 DEX 이후 NAVER 계정이 남으면 `naver_account_cleanup.py`로 삼성 설정의 네이버 계정 제거 절차를 진행합니다. 시스템 계정이 사라져도 지도 내부 세션은 남을 수 있어, 1.1.17부터 PC와 휴대폰 앱 모두 계정 단계에서 지도 데이터도 반드시 초기화합니다. 사용자 0의 완전한 현재 계정 목록을 검증하며, 조회 실패·제거 거부·지도 데이터 초기화 실패·비삼성 계정 잔존은 실패로 표시합니다. PC는 마지막 단계 후에도 계정 목록을 다시 확인합니다. 계정 이름이나 DEX 원문을 로그에 기록하지 않습니다.

동봉 APK 버전과 맞는 `windows-v*` 태그(예: `windows-v1.1.17`)를 푸시하면 **Publish Windows EXE**가 준비·계정 테스트와 시뮬레이션 후 EXE를 빌드합니다. 기존 앱 릴리스의 공개 APK·업데이트 JSON이 동봉 파일과 정확히 일치하는지 검증하고 Windows ZIP·체크섬만 추가합니다. 앱 APK와 자체 업데이트 파일은 교체하지 않습니다. 릴리스 설명에는 EXE 소스 커밋을 기록합니다. 게시 전에 실패한 빌드는 `-build2` 같은 태그로 재실행할 수 있습니다. 기존 배포 파일을 덮어쓰지 않으므로 이미 게시한 Windows 버전을 수정하려면 새 버전을 사용하세요.

### 1.1.18 비활성 인증 앱 및 진행 화면

Android 앱과 PC는 실제 사용자 0 계정 목록을 기준으로 `account_preparer.dex`를 실행합니다. 헬퍼는 설치 APK의 `android.accounts.AccountAuthenticator` 메타데이터를 비활성 앱까지 조회하여, 남아 있는 비삼성 계정의 인증 앱만 활성화·검증합니다. 일반 계정 API는 비활성 계정을 숨길 수 있으므로 준비 대상 판정에 사용하지 않습니다. 삼성 계정 제공 앱은 공유 패키지도 보호합니다. 계정 제거 후 지도·Meet의 로컬 로그인·저장 데이터를 삭제하고 잔존 계정을 확인합니다. 준비한 앱은 활성 상태로 남습니다.

Android shell은 일반 앱의 개별 컴포넌트 활성 상태를 바꿀 수 없습니다. 인증 서비스 자체가 비활성인 경우 헬퍼는 실패하며, 남은 계정을 무시해 완료로 표시하지 않습니다. 일반적인 앱 전체 비활성화와 구분합니다. 설치된 필수 앱은 최신 버전이라 설치를 생략해도 다시 활성화하며, 앱 데이터 초기화 결과도 검사합니다.

진행 화면은 바깥 스크롤을 제거하고 상단 진행률을 고정합니다. 남은 높이를 진행 기록 박스가 차지하며 해당 박스만 자동 스크롤합니다. 실제 검증 범위와 테스트 실행법은 [비활성 앱 검증 기록](../docs/disabled-app-verification.md)을 참고하세요.

새 워크플로가 Actions 목록에 보이지 않으면 기본 브랜치에 워크플로를 반영하거나, 해당 코드가 있는 커밋에 `app-v*` 태그를 붙여 푸시하세요.

로컬에서 게시 파일만 미리 준비할 수도 있습니다. 이 명령은 GitHub에 업로드하지 않습니다.

```sh
python tools/prepare_app_release.py
```

결과는 `release-app/`입니다. 자체 업데이트 기능이 없는 **1.1.10 이하 기기는 이번 버전을 EXE/USB로 한 번 설치한 뒤** 이후 릴리스를 앱에서 업데이트할 수 있습니다.

### 1.1.19 네이버 지도 준비 검사

Android 앱의 `prepareNmap`과 PC의 `verify_nmap_ready`는 지도를 실행하지 않고 설치·번들 이상 버전·실제 활성 상태만 확인합니다. 활성화 후 `pm list packages -e --user 0`에서 패키지가 확인되어야 완료입니다. 실행 화면 조회, 앱 시작, 2초 대기, 실행 프로세스 검사와 강제 종료는 제거했습니다. 계정 단계의 네이버 계정·지도 로그인 데이터 초기화는 유지합니다.

### 1.1.20 필수 앱 준비 중 프로세스 종료 방지

18단계에서 초기화 앱 자신에게 `pm enable`을 보내면 manifest 기본 활성 상태에서 명시적 활성 상태로 변경되는 과정에 실행 프로세스가 종료될 수 있습니다. `ensureEnabled`는 실제 활성 목록을 먼저 읽어 이미 활성인 앱의 상태를 바꾸지 않습니다. 초기화 앱과 Shizuku는 실행 기반이므로 휴대폰 초기화 중 활성 여부만 검증하고 직접 상태를 변경하지 않습니다. 다른 필수 앱은 비활성일 때만 활성화한 뒤 결과를 다시 읽습니다. PC 준비 경로도 `_ensure_package_enabled`로 이미 활성인 앱을 건드리지 않습니다.

### 1.1.21 REST API 없는 업데이트 확인

`AppUpdater.check`는 `https://github.com/w00ye0l/galaxy-reset/releases/latest/download/galaxy-reset-update.json`을 직접 읽습니다. GitHub REST API와 앱에 내장한 토큰은 사용하지 않습니다. 메타데이터의 `versionName`이 숫자 세 자리 버전 형식인지 확인한 뒤 해당 `app-v<versionName>` 릴리스의 APK 주소를 생성해, 최신 릴리스 변경과 다운로드 간의 버전 혼동을 방지합니다. 허용된 HTTPS 다운로드 호스트와 SHA-256·서명·패키지·버전 검증은 유지합니다. 앱의 다운로드 허용 목록에서 `api.github.com`도 제거했습니다.

1.1.20 이하의 조회 경로가 제한된 상태에서는 GitHub 릴리스의 APK를 직접 설치하거나 갱신된 EXE로 한 번 업데이트할 수 있습니다. 기존 앱 삭제나 데이터 초기화는 필요 없습니다. 파일 다운로드 서버의 일시 장애·403·429까지 없어지는 것은 아니며 해당 오류는 계속 표시합니다.

### 1.1.22 Knox Configure 보존

`com.sec.knox.kccagent`만 Android `KEEP`와 PC 삭제 제외 목록에 추가했습니다. 기기 관리자 해제가 잠겨 있더라도 이 패키지는 삭제를 시도하지 않고 ‘Knox Configure 관리 앱 보존 · 관리자 등록 유지’로 기록합니다. 다른 사용자 앱 삭제 실패를 무시하는 처리는 하지 않습니다. Knox의 관리자 권한과 설정은 그대로 남습니다. 이 앱의 보존은 고객 계정·미디어·파일 정리와 별도이며 관리 등록 해제 완료를 뜻하지 않습니다.
